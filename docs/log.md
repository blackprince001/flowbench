## 2026-07-30

- **Prompt diff view (issue #45).** The results-server answer to "how are my prompts doing": a `/runs/{id}/prompts` tab listing every observation a run recorded, and one comparison at a time — two variants within the run, or the same variant against an earlier run of the scenario. Diff-and-assert only; nothing here scores a completion or calls a model to judge one.

  **The prompt is part of the comparison, and it leads.** An output that moved under a changed prompt is the author's edit, not the model drifting, and a page that showed only the completions would let those two be confused permanently. So the card states its verdict before the diff: *prompt changed* (amber, with the prompt's own diff above the output's) or *same prompt*, naming the hash both sides carry. That is the whole reason #43 hashes prompt identity.

  **Two granularities, because one cannot read a completion.** Lines pair the sides so they sit beside each other; within a paired line, words are diffed again, so a one-word edit reads as one word rather than as a rewritten paragraph. Built rather than adopted for ADR 0014's reason — the input is two strings the store already holds, the output is server-rendered HTML sharing this stylesheet, and a JS diff component would be a dependency, a build step and a second visual vocabulary for an algorithm that is a page long.

  Three things the work turned up. **A chat prompt is recorded as one line of JSON several hundred characters wide**, and a line diff over one line can only say "this line changed" — so a pair that is both JSON is re-indented for display, and *both or neither*, since pretty-printing one side alone manufactures a difference on every line. **Whitespace had to become its own token**: attached to the word before or after it, a one-word highlight lit up the space beside it and an indented line looked changed to its margin. And **neither mark relies on colour** — the deletion is struck through, the addition underlined — because red and green are one colour under deuteranopia, which is the rule the status palette has followed since ADR 0014.

  Structural diffs ride the same page when both completions parse as JSON: each changed field is named by the JSONPath an assertion could use. Token usage sits beside the diff as counts rather than rates — a completion that grew by 38 tokens says so, and a percentage over a two-run sample is arithmetic dressed as a trend. Layout (side-by-side or inline) and both sides of the comparison are URL state like every other selection in the report, so a diff worth discussing is a link rather than directions to click. Acceptance executed against two real runs around a prompt edit: the edited variant flags its changed hash and diffs both prompt and output; the untouched variant reports the same hash and an empty diff.

- **Runs are tabs now.** The left rail lists a project's runs, but comparing two meant leaving one to look at the other. Runs a reader has opened now sit in a window-style strip across the top: a coloured badge carrying the scenario's first letter, its name, its time, and a close button on hover.

  **The colour and the letter are derived, never stored** — hashed from the scenario name into the same validated categorical slots the span kinds use — so every run of one scenario looks alike and the strip is scannable without being read.

  **Which runs someone is holding open is theirs, not the store's.** The server is read-only and stateless, and two people reading one store are not reading the same three runs, so the list lives in `localStorage` and the server renders exactly the page it is serving. With JavaScript off the strip is a correct one-tab strip rather than a broken many-tab one — the same progressive-enhancement line the flame graph's viewport draws. Visiting a run opens it; re-visiting moves nothing, because a tab that jumped to the front whenever you looked at it would never be where you left it; closing the one you are reading lands on its neighbour, the way a browser does it. Twelve tabs is the cap.

- **gRPC streaming is out of v1 (ADR 0019, spike #29).** Resolved the last PRD open question M3 was holding, and the last issue in the milestone. Unary only; a streaming method stays a pre-run error, now naming the decision rather than a pending question.

  **The spike's finding is that the stated objection had expired.** The PRD deferred streaming because "the step and span model is call-shaped" — but #27 already grew both pieces streaming needs: a session that outlives the step which opened it (iteration-scoped, closed in a `defer`, its graph resolved pre-run by the validator) and the rule that an arriving message is not a response (`match` selects, `assert` judges, everything else is `skipped`). A server-streaming call maps onto that almost exactly, and the response is already JSON (ADR 0018), so extraction, assertions, capture and folding would apply unchanged. If the question were only "does it fit", the answer is yes.

  **What decided it is one level up, in the profile model.** A run reports iterations/sec, per-flow-run percentiles and an arrival cap — a vocabulary about discrete flow-runs. A bidi stream held open for minutes turns 500 VUs into 500 concurrent streams and makes every one of those numbers describe nothing: throughput counts stream *opens*, p95 measures the flow-run that contained a stream rather than the stream, the cap governs openings rather than traffic. WebSocket sessions dodge this by being exchanges rather than subscriptions; streaming's characteristic use is the subscription. Saying what such a run measured is a second vocabulary, not an adapter.

  Two supporting costs, and one absence. Three kinds each need their own step semantics in both surfaces, with conformance fixtures and a dynamic streaming stub; a stream's **status arrives in the trailers**, so a `RESOURCE_EXHAUSTED` shed mid-flight is discovered at close and would be blamed on whichever step drains the stream; and client streaming **blocks on HTTP/2 flow control**, so a VU stalled in `SendMsg` reads as a slow call unless blocked-on-flow-control becomes its own span. Meanwhile nobody has asked: streaming RPCs in an internal estate are mostly telemetry, log tailing and pub/sub bridges, which have their own suites, and the streaming case a team would actually bring today — token-by-token model output — is HTTP SSE, which the Python-driven path already instruments.

  The ADR records **how the three kinds would map** so that adding it later is additive rather than a redesign, and names the trigger: a team with a streaming RPC inside a flow they want to test. Server streaming alone would be the slice. One thing is stated rather than implied — **there is no escape hatch**: a Python-driven flow calling a streaming RPC through its own generated stubs travels over `grpc-python` rather than httpx, so nothing is recorded and the step earns no span at all. A flow that must exercise a streaming RPC in v1 does it outside FlowBench.

  **M3 is complete.** Engine as an importable package with a Python-driven execution path, SDK-side HTTP auto-instrumentation (sync and async), GraphQL, WebSockets, gRPC unary, prompt observation with variants, auth scheme coverage, and agent v1. Two items in the original description are not built and are decided rather than outstanding: the DB verifier (cut, PRD v0.7) and gRPC streaming (this ADR).

- **Dropped the DB verifier (issue #31 closed, PRD v0.6 → v0.7).** Product call, taken while scoping the work rather than after building it. - **Prompt variants, and the rename warning that turned out not to exist (issue #44).** Variants are labels, not machinery: `variant="concise"` gives an observation its own structural identity (`classify@concise`) and the author's own code decides what varies. The mechanics rode in with #43 — the label is part of the span name, the payload carries it, and each variant's own template hashes to its own identity — so the acceptance was the work: two variants of one observation, recorded in one run, showing separate span paths, separate captured completions and separate hashes in `traces.json`, and folding apart under the step so per-variant counts stay per-variant.

  **The issue said the existing parser warning covered variant renames. It does not, in two ways.** `Options.PriorStepIDs` compares *declared* step ids in the IR — and an observation is declared nowhere, it exists because a step's body opened one, so the parser structurally cannot see it (ADR 0012: the Go path runs no Python). It is also fed `nil` at its only call site, so it has never fired in a real run at all. Reporting that gap and moving on would have left the issue's own stated concern — "variant renames break cross-run folding the same way step renames do" — with nothing behind it.

  **So the warning is implemented where variants live.** A run now records the structural identities it used — its steps, and the observations its code opened, as the dot-paths folding keys them by (`classify.classify@concise`) — into `meta.json`, and the next run of the same scenario warns about any that has gone. The comparison has to be against a previous run rather than against a declaration, because discovering an observation is what *running* does. `None` and the empty set are deliberately different when reading the prior run: one means the run predates the field (or a Go-produced run wrote none), the other means it genuinely recorded nothing, and only the second is grounds for a warning.

  **Only a clean run is grounds for it.** A run that failed part way stopped short of identities it would otherwise have reached, and reporting those as renames would blame the author for the failure they are already looking at — a test pins that, since it is the one false positive this design can produce. `store.Meta` gained the field on the Go side too, for the same reason the observation payload did: the run store is one format two producers write.

  Still open, and now stated rather than assumed: the YAML/Go side warns about nothing, because `PriorStepIDs` is unwired. Feeding it from the store is a small piece of work on `cmd/flowbench/run.go` and belongs to whoever picks up the step-rename half.

- **Prompt-observation API (issue #43).** `with ctx.prompt("classify") as p:` … `p.record(prompt, completion, usage=...)` around the LLM call the flow's own code makes. FlowBench does not make the call, template the prompt, or set a model parameter — ADR 0009's whole point — so the API is four things only the call site can do, and nothing else.

  **The span is the reason this is small.** #24 put the hook on `httpx.Client.send`, so the provider SDK's round trip was already being recorded; the observation only has to be the parent it hangs off. `Instrumentation.enter_scope` moves the recording parent from the step to the observation for the duration of the block, which is the entire integration — `classify` → `POST /v1/chat/completions` → `http_call` → phases, with no adapter, no provider matrix, and nothing that knows an LLM from any other HTTP service.

  **Identity is `template=` when there is one, content otherwise.** A prompt whose variables differ every iteration would otherwise get a different hash every iteration, which makes the run-over-run comparison #45 exists for say only "everything changed". The author declaring the template is what makes the hash stand still while the substituted values move — and the fallback is honest rather than clever: with no template the recorded content *is* the identity, and it moves when a value does.

  **A pace wait is a span of its own, beside the observation.** `pace="20/m"` is a token bucket keyed by the observation's *name* rather than its span identity, so two variants of one prompt share the ceiling declared for it — they hit the same provider. Bucket state is module-level, because a LiveDriver lives for one iteration and a ceiling that reset every iteration would not be a ceiling. The wait is charged to the bucket before it is slept, so concurrent callers queue rather than waking together. It gets its own `pace` span rather than being folded into the observation's, for the same reason a retry's `backoff` is separate: it is the flow's own waiting, and folding it in would inflate every latency figure the observation reports.

  **`timeout=` is measured, not enforced, and says so.** The call belongs to the author's SDK and FlowBench holds no handle to cancel it, so an overrun is reported after the call returns. Pretending otherwise would have meant a thread and a cancellation story for a call we do not own; the docstring names the limit and points at the SDK's own timeout argument.

  Four things fell out of the work. **`p.completion` is a `str` subclass**, so the flow's own code can slice, parse and chain it like any other string *and* `expect(p.completion).to_contain(...)` works — PRD 10.9's "ordinary `expect(...)` calls, no special machinery" turned out to be a two-line class rather than an assertion surface. **A recorded observation now earns a step its span**, alongside `ctx.http` and an instrumented call: not every client is one instrumentation can see — a `requests`-based SDK, a model that is not reached over HTTP — and an exchange is evidence of work whatever carried it. **A step that already failed is exempt from the "made no HTTP call" rule**, which was a latent bug the prompt path made reachable: a provider client throwing before it got a request out produced "step made no HTTP call" laid over the top of the real failure. And **FlowBench's own errors stay loud inside the block** — a `FlowExecutionError` is the flow being written wrong and must not become recorded data, while the provider's exception is exactly what should.

  On the store side the payload gained `prompt`, `completion`, `prompt_hash`, `variant` and `usage`, and **`internal/span.Payload` gained them too** even though the engine never writes one: the run store is one format two producers write and the results server reads, so without the Go fields a Python-recorded exchange would decode away to nothing on its way into the diff view. Token counts are normalized to one vocabulary on the way in (OpenAI says prompt/completion, Anthropic input/output) rather than leaving the reader provider-specific; usage that carries no count at all is refused rather than dropped.

  Acceptance green: a two-row data pool against an OpenAI-compatible stub writes both iterations' prompt, completion, hash and token counts into `traces.json` under one stable hash; a stubbed `429` reports `throttle_rate 1.0` with `error_rate 0.00` and still captures the pair. A flagged key inside a prompt appears in no artifact, and `flowbench run` on a flow that observes a prompt is refused with the reason (ADR 0012: the Go path runs no Python, so there is nothing there to wrap).

- **Async HTTP is recorded now, and a stack became a ContextVar (extends #24).** `AsyncOpenAI` and its equivalents are how a great deal of provider code is written, so an observation that could only see the sync client was going to be opaque exactly where #43 needs it not to be. Patching `httpx.AsyncClient.send` is the small half; the reason it was left out originally is the other half.

  **Concurrency broke two assumptions, both of which were a global.** The in-flight call was a LIFO stack on the Instrumentation, which is only correct while requests nest — under `asyncio.gather` three requests are open at once, so "the most recently started" is the wrong owner for both an arriving phase event and a new request's parent: a slow response's `receive_response_headers` would have closed a *different* request's `ttfb`, and the calls would have nested inside one another arbitrarily. The stack is gone. The current call lives in a ContextVar, and each request's trace callback is bound to **its own frame** rather than to the recorder — a task copies the context when it is created, so sibling coroutines cannot see each other's frames, while a request genuinely made inside another still nests. The test that pins it gathers three calls against endpoints sleeping 200/100/0 ms and asserts each span's `ttfb` matches its own endpoint; under the old stack they would have been shuffled.

  **httpcore refuses a plain function on the async interface**, so the frame carries both a sync `trace` and an `atrace` coroutine, and the chaining that preserves a caller's own trace extension has to match the interface the request will travel on. Recording is otherwise one code path: sync and async `record` differ by an `await` and nothing else, since everything around the call is the same open/close pair.

  Two things the change does not do, stated rather than discovered. Overlapping siblings can sum to more than their parent's duration, so a flame graph over a batched step shows where the time went and not a timeline you can lay a ruler against — inherent to concurrency, not to this implementation. And **two prompt observations open at once are still unsupported**: the recording parent is driver state rather than per-task, and the pace guard sleeps the thread, so a batch of concurrent `ctx.prompt` blocks would cross their spans and serialize on the guard. Gathering the calls inside one observation is the supported shape and is tested. `requests` and other non-httpx clients still pass through unrecorded, and a call made on a spawned *thread* still is not recorded — a thread starts from an empty context, unlike a task.

## 2026-07-28

- **SDK-side HTTP auto-instrumentation (issue #24).** The Python-driven path could only see calls made through `ctx.http`, which is exactly the wrong half: under ADR 0012 the calls that matter are the ones the flow's *own* code makes — its helpers, its client, the provider SDK #43 will wrap — and FlowBench never gets handed those. So the hook goes on the class rather than on a client we hand out: `httpx.Client.send` is patched once per process and every request made while a driver is attached is recorded. With no driver attached it passes straight through, so importing `flowbench` does not quietly instrument a process that never runs a flow.

  **Phases came from httpcore's `trace` extension**, which is its httptrace — `connect_tcp`, `start_tls`, `send_request_headers`, `receive_response_headers`, `receive_response_body` map onto the `connect`/`tls`/`ttfb`/`transfer` children `internal/adapters/http.go` already emits, one `http_call` leg per redirect hop, legs closing at hop boundaries the same way. One phase does not survive the crossing: **httpcore resolves the hostname inside `connect_tcp` and traces no DNS event of its own**, so a Python-produced `connect` covers resolution too and there is no `dns` sibling. Faking one would have meant resolving a second time, which is a measurement of a request that never happened; the gap is left visible and named in the docstring instead. `ctx.http` now routes through the same recorder and gained the phase children it never had — the step span *is* the call span there, so its shape stays byte-identical to the engine's.

  **Naming is the decision with consequences.** Folding is by span name (ADR 0007), so calling every recorded request `http_call` would have folded three different endpoints in one step into a single flame frame — Python resolving into one opaque node instead of one opaque blob. They are named `POST /v1/chat/completions` instead, with digit, hex and UUID-shaped path segments normalised to `:id`, because the alternative — raw ids — gives a fifty-row data-pool run fifty flame frames. That is a cross-run identity contract, and a rename breaks folding the same way a step rename does.

  Two consequences fell out. A step no longer has to touch `ctx.http` to be a step: it earns its span by putting a request on the wire *somehow*, which is what lets #43's prompt step exist at all — a step that still calls nothing is an error, as before. And a `429` from a call the SDK made has no assertion to be classified at, so it is marked `throttled` where it happened and bubbles up with the step rather than aborting third-party code mid-flight.

  **Redaction needed a way in.** The Go engine sees every credential because the flow declares it as `{{ env.* }}`; a Python flow's provider key is read from the environment at import scope by code FlowBench never touches. `flowbench.secret(value)` is the handover — module-level precisely so it works before any run exists, returning the value so it can wrap an expression in place — and each run seeds its `SecretSet` from what has been flagged. `ctx.secret(...)` covers values the step computes. `secret.py` became `redaction.py` so the public function is unambiguously `flowbench.secret`.

  Limits, stated rather than discovered later: sync `httpx.Client` only (async clients and `requests` pass through unrecorded), and the active driver lives in a ContextVar a spawned thread does not inherit, so a call made off-thread is not recorded — the safe direction, since the span tree is built without locks. Acceptance green: a flow whose own client makes three calls in one step writes three spans with phase timings to the run store, distinct in `traces.json` and in the fold; a flagged token appears in no artifact.

- **The mono is JetBrains Mono now.** The report set machine facts — run ids, timestamps, span paths, tile labels — in whatever monospace the reading machine happened to have, on the reasoning that a terminal face is what machine facts should look like and it costs nothing to ship. The cost turned out not to be zero: the same run id had a different width, weight and figure shape on every machine, and a column of ids that lines up on a Mac and not on Linux is a table that only works where it was written. JetBrains Mono (SIL OFL 1.1) ships in the binary beside Open Runde, cut to latin/latin-ext plus the seventeen non-ASCII glyphs the report actually draws — 126 KB for three weights, down from 280 KB unsubset, and about 330 KB for both faces together. The platform stack stays behind it, so a glyph outside the subset still falls back per glyph rather than failing.
- **Outcomes over time is a shape now, and the run page gained a funnel.** The outcome strip was a row of stacked columns, which makes a reader compare heights one pair at a time. A run is one continuous thing, and the question the strip exists to answer — *when* did the throttling start — is a question about a shape, so the same buckets, the same shares and the same links are drawn as three stacked ribbons instead. Nothing about the interaction changed: every bucket keeps its own link, tooltip and selection as an invisible hit area over the bands, and the tallies row above still states each outcome in words, because colour is never the only carrier here.

  **The funnel is the new question.** A step's folded count is how many flow-runs reached it, so the narrowing between two stages is exactly the flow-runs that did not get past the first — "where do flow-runs stop", which is neither what the flame graph answers (where time goes) nor what the waterfall does (what happened in this one). Two tiers each supply the half they are honest about: **counts come from the fold**, which sees every iteration, and **order comes from a kept trace**, because `FoldNode.Children` is a map and a funnel drawn in map order is not a funnel. Without a kept trace there is no funnel at all rather than an invented order, and a one-step flow is a number the tiles already show.

  Three things the work turned up. A step **no flow-run ever reached has no fold node**, because no span was ever created for it — so the first draft silently dropped it, turning the most interesting funnel there is ("nobody got past step one") into one that looks like the flow ends at step one; unreached steps are stages at zero now. A stage holding 0.2% would be invisible at true scale, so it is floored at a hairline and the exact count is printed on it — the fold is in the thickness, never in the number. And a **flat funnel is a finding, not an empty state**: in load/stress/soak the mode default is `record`, so a failure is data and the flow carries on, which means a healthy load run should be flat — it says "no flow-run stopped early" in words rather than leaving a reader to infer it from equal widths. Verified against a flow whose first step aborts: 7,320 → 7,314 → 7,314, with `−6 flow-runs here` on the stage that lost them.

  `StreamOf` takes the strip's own cells rather than a second copy of the series, so there is one place a bucket's shares are worked out and the graph cannot disagree with what it links to. `segHeight` went with the columns it sized.

- **Each example is its own project.** `examples/run-all.sh` used to pour every example into one store, which read as one pile of runs that happened to share a directory — but they test different services, under different profiles, against different stubs. Each example writes into `<store>/<example>/` now and `serve` gets one `--store name=dir` per project, so the split needed nothing added to the results server: the multi-project workspace already existed and this is just where the runs land. Five projects from the local examples, nine with `--public`.

  And `serve` finds them: a directory holding an `index.json` is a run store, one that only *contains* such directories is expanded into a project each, so `flowbench serve --store runs` shows all nine rather than nothing. A run's own directory never has an `index.json`, which is what keeps individual runs from being reported as projects, and an explicit `name=dir` is always taken literally — naming a project is a statement that it is one. The discovery runs at startup, which is why the script still names its projects when it starts the server first: their directories are empty at that moment, and watching them fill is the point.

- **gRPC unary adapter (issue #28).** A `grpc` step type: unary calls described by the team's own `.proto`, with `RESOURCE_EXHAUSTED` classified as `throttled`. GraphQL rode on the HTTP adapter and WebSocket rode on its handshake; this one does not ride on it at all, and the interesting parts are what that costs and what it does *not*.

  **No code generation, ever.** The usual Go answer is `protoc` plus generated stubs, and it is the wrong answer for a testing tool: the schemas belong to the services under test, so generating from them means a toolchain in every contributor's path, or rebuilding the *engine* when a target adds a field. A flow names a `.proto` and a fully-qualified method, and the engine compiles it at run time (`bufbuild/protocompile`), builds the messages dynamically (`dynamicpb`), and converts both directions with `protojson` — ADR 0018. **Compilation happens once per run, before the first request**, next to the host allow-list and the VU ceilings: a missing file, a typo'd method or a streaming method is a pre-run error that lists the alternatives, rather than something 10k VUs each discover separately. The compiler's reach is a pinned dependency's property rather than a claim — proto2, proto3 and edition 2023 all compile, and a test says so instead of this paragraph.

  **The response being JSON is the whole trick.** It is what lets `$.chargeId` extraction, body assertions, capture, redaction and folding be the same code a `call` step uses, and it is why the slice is small. The same descriptors serve as well as call, so `internal/grpcstub` turns a schema plus a few JSON handlers into a server — no generated code on the stub side either, which is what makes the worked example and every fixture possible without a build step.

  **A gRPC status is a real status, so the HTTP rule applies unchanged.** GraphQL needed a special reading because it hides failure inside a `200 OK`; gRPC puts its verdict in the status, exactly where HTTP puts it. So a non-OK code is *data* — it does not fail the step on its own, and a flow that cares says `status == 5` — and there is no `on_error` policy to invent. The one line that had to be drawn is between a verdict and no answer at all: `UNAVAILABLE`, `DEADLINE_EXCEEDED` and `CANCELLED` are the codes gRPC generates for the channel and the deadline rather than for the service, so they are failed calls. Without that, a run against a dead target would report 0% errors, and the acceptance test would pass against nothing.

  **`throttled` reached through a numbering that shares nothing with HTTP's.** `RESOURCE_EXHAUSTED` is code 8, and nothing in gRPC is 429 — so the classifier is separate rather than reused, and a step mapping further codes writes them in gRPC's numbering (`14` is UNAVAILABLE). The throttle is classified **before** the transport's own verdict, which is what lets an author whose gateway sheds load with UNAVAILABLE get a throttle rather than a failure — ADR 0006's "a throttle is a throttle whatever else is true of it", showing up where it actually bites. Verified against the example stub shedding past 30 concurrent charges: **96.78% throttled, 0.00% errors** over 218k iterations, with `error_rate < 1%` holding.

  Three things fell out of the work. **The retry loop is protocol-agnostic now**, and gRPC is why: `UNAVAILABLE` is both an error and the code a retry policy most wants to name, so breaking the loop on `err != nil` made `on_status: [14]` useless. It now breaks on "no status at all" instead — unchanged for HTTP, where a refused connection has no status either way — and one `withRetry` serves both adapters rather than the loop being copied. **The report learned that not every status is HTTP's**: `statusLabel` rendered a bare number as `HTTP %d`, which would have turned code 8 into "HTTP 8", so a span can now carry its status in its own protocol's words and the failure drill-down groups on `RESOURCE_EXHAUSTED`. And the phase spans had to be re-derived rather than inherited — gRPC brings its own HTTP/2 client, so there is no `httptrace` — which a `stats.Handler` does: a 120-VU capacity run folds to 120 `connect` spans, one per VU, `ttfb` on all 218k calls, and `transfer` only on the 7k that carried a message back, because a shed call has nothing to transfer. Acceptance green in both halves: a unary chain (charge → extract id → refund → refund again, asserting the `FAILED_PRECONDITION` the service really sends) passes against the stub, and `grpc_unary` proves both surfaces compile to byte-identical IR. Worked example in `examples/grpc-local/`.

## 2026-07-26

- **WebSocket adapter (issue #27).** A `ws` step type: open a session, send and receive matched messages across steps, assert on received frames. GraphQL was HTTP with one extra reading of the body; this one breaks the shape the engine has assumed since M1, in two places.

  **A session outlives the step that opened it.** Every step type so far was call-shaped — build a request, get a response, extract, assert, done. A WebSocket connection is state: one step opens it, later steps work on it, and it is closed when the *iteration* ends, not when a step returns. So sessions live on the `Iteration` and `RunFlow` closes them in a `defer`, which is the whole implementation of "iteration-scoped" and covers the abort paths for free. A step names the session it wants (`session:`, empty being a name like any other), and — the part that earns its keep — **the validator resolves the session graph before the run**, exactly as it already resolves the variable graph: a step working on a session no earlier step opens is a pre-run error with file:line, not a nil map at request time. Opening the same name twice is refused for the same reason.

  **A frame is not a response.** Nothing correlates an arriving frame to the message that preceded it — heartbeats, other subscriptions, server pushes all land on the same wire. Classifying "the next frame" as the answer makes every flow against a chatty feed flaky, so a receive states what it is waiting for and everything else is *skipped*, not failed on. That splits two things that look identical in YAML and do opposite jobs: `match` **selects** the frame the step is about, `assert` **judges** the one match selected. Unmatched frames are dropped rather than buffered for later steps — a test that depends on the ordering of traffic it never asked for is a test that will flake — and the cost is paid where it shows: a timed-out receive reports the conditions in the flow's own words plus the first few frames it passed over, because without them a healthy target reads as a hang. A frame has no status line and no headers either, so `status ==` and `header.X ==` on a ws step are refused at parse time instead of being answered with a misleading zero; `latency` stays, and means the time spent waiting.

  **Throttling arrives after the connection is open.** RFC 6455 close code `1013` is "try again later" — the WebSocket's `429`, from a server shedding load on a connection it had already accepted — and it classifies as `throttled` (ADR 0006), feeding `throttle_rate` rather than `error_rate`. Every other close code fails and names itself, so `1011 internal error` and `1013` are visibly different events. A handshake refused *before* the upgrade is an ordinary HTTP response and classifies as one, `Retry-After` and all. Verified against a stub carrying 40 of 120 requested sessions: **45.66% throttled, 0% errors.**

  **The handshake is just HTTP, and that decided the library.** A WebSocket opens with a `GET` carrying `Upgrade: websocket`, so everything already built for requests should apply to it. `github.com/coder/websocket` (ADR 0016) is the only maintained Go client that dials through an `*http.Client`, so the adapter hands it the session every call step uses and gets the cookie jar, the auth schemes from #30, the host allow-list, and the `httptrace` phase spans unchanged — a `ws_open` span carries the same `http_call` → dns/connect/ttfb children a `call` step does. Hand-rolling RFC 6455 was the alternative and was rejected: masking, fragmentation and the close handshake are ~400 lines of protocol that is not this project's contribution, and the part that *did* need integrating was the handshake, which the library already does right. The allow-list learned that `ws://host` and `http://host` are one origin, so a target lists its host once.

  Two things fell out of the work. Running the example found a bug the tests had missed: a receive deadline landing *mid-message* tears the connection down (a half-read WebSocket message cannot be resumed), and the error surfaced as "use of closed network connection" — blaming the target for the flow's own mismatch. Timeouts are now identified by the deadline rather than only by the error, with peer closes still taking precedence so a `1013` is never swallowed; a chatty-feed test pins it. And the Python surface gained body assertions (`expect(r.json_path(...))`) it never had, because a frame's body is the only thing a ws step *can* assert on — plus `frame(...)` for match conditions, and `Flow.compile` now mirrors `ir.Step.MakesRequest` so a flow-level credential reaches the handshake and stops there. Live execution refuses `ctx.ws()` and points at the Go engine, as it does for GraphQL. Acceptance green: a session opened, matched messages exchanged across two steps, a frame asserted, and the server seeing the connection close when the iteration ends; `ws_session` proves both surfaces compile to byte-identical IR. Worked example in `examples/ws-local/`.

- **GraphQL adapter (issue #26).** Query and mutation steps with variables, extraction over the `data`/`errors` shape, and — the substance of the slice — an outcome classification that GraphQL forces us to think about properly.

  **GraphQL rides on the HTTP adapter rather than beside it.** An operation is a POST of `{query, variables, operationName}`, so `runCall` and `runGraphQL` now share one `request` path: the session and cookie jar, the per-phase spans (a `graphql` step carries the same `http_call` child with dns/connect/tls/ttfb/transfer beneath it), retry policy, `429` → throttled, the host allow-list, and the auth from #30 all come across unchanged. What the adapter adds is the request body shape and one reading of the response. That reuse is the reason the slice is small, and it is the shape #27 and #28 should follow.

  **A failed operation answers `200 OK`.** GraphQL puts the transport's verdict in the status and the operation's in the body, so "classification identical to HTTP" cannot mean "classify off the status" — that scores every broken query as a pass. Decision: **a non-empty `errors` array fails the step by default**, and the author opts out rather than having to remember to opt in with an assertion. The alternative — errors are data the flow asserts on — is more literally HTTP-like, but a flow that forgets one assert then reports a broken query as green forever, and a load run would report a graph erroring on every request as 0% error rate. Two escapes on the `graphql` block: `on_errors: allow_partial` fails only when the operation resolved no data at all (the federated case, where one subgraph times out and the rest answer — extraction still runs over the half that resolved), and `on_errors: ignore` hands the judgement back to the flow's own assertions. A body that is not a GraphQL document at all — a proxy's HTML error page — fails under the first two, since nothing can be extracted from it. Errors keep their `path`, so a failure names the field (`product.costPriceCents`) rather than only the message, and folds under its own `graphql_errors` span so a run where one query kept erroring is visible in the flame graph.

  **Values reach an operation as variables, never spliced into the document.** `{{ }}` in `variables` resolves through the JSON-escaping resolver call bodies already use, so an extracted value keeps its JSON type (a quantity arrives as a number the schema can check) and a value full of quotes and braces cannot rewrite the query. Templating the query document is deliberately unsupported and the variable-graph checker skips it.

  Two things fell out of the work: goccy models a `|` block scalar as a `LiteralNode` rather than a `StringNode`, so `w.str` rejected every multi-line query — the new `w.text` accepts both, and any future multi-line field gets it free. And `ir.Step.MakesRequest()` is now exported and shared by the parser's auth flattening and the validator, because they had drifted: a `graphql` step was silently not inheriting flow-level auth. Acceptance green: a query→extract→mutation chain against a GraphQL stub in integration mode, with the stub dispatching on the operation it actually received; `graphql_operations` proves both surfaces compile to byte-identical IR. Worked example in `examples/graphql-local/`.

- **Auth scheme coverage (issue #30).** Every scheme the PRD names — bearer/JWT (static or extracted at runtime), basic, API keys in a header or query, session cookies, OAuth2 client-credentials, HMAC request signing — declared on a step or once at the flow level, in both authoring surfaces. Authorization-code stays out; it needs a browser. New `internal/auth` package holds the appliers and the run's shared token cache. `ir.AuthSpec` is one flat block whose set fields are checked against *the scheme's* vocabulary, so `password:` under `scheme: bearer` is a parse error naming both rather than a credential that silently never gets sent.

  **Flow-level auth is sugar, resolved at compile time.** The endpoint catalog that would own "declare once" (PRD 10.1) is still P1 and unbuilt, so a flow-level `auth:` block stands in: both surfaces flatten it onto every request-making step that did not declare its own and drop `scheme: none` opt-outs — the same move YAML's `data:` shorthand makes when it expands into a data pool. The executor therefore never looks at the flow; it reads `step.Auth` and nothing else, and the conformance suite holds the two spellings to byte-identical IR. One consequence is worth knowing: a flow-level bearer carrying a token the *login step* is about to extract fails the variable graph **on that step**, because it cannot send what it has not fetched yet. `auth: { scheme: none }` there is the fix, and the error says so with file:line.

  **Credentials are attached per attempt, not per step.** A retried request is signed afresh instead of replaying the first attempt's timestamp, which any server enforcing a signing window would reject.

  **Redaction covers what auth *derives*, not only what it resolves.** `{{ env.* }}` values were already registered by the scope on the way past; the basic blob and an OAuth2 access token are registered now too, since one decodes straight back to the password and the other stands in for the account. The HMAC signature deliberately is not: it is per-request and not reversible to the secret, and registering one per request would grow the redaction set without bound and charge for it on every scrub at 10k VUs.

  **The OAuth2 token endpoint sits inside the host allow-list.** It is a real outbound request carrying client credentials, so `token_url` is gated exactly like a call — pre-run when it is a literal, at request time when it is templated. Without that, naming any host as `token_url` would ship env-sourced credentials straight past the safety gate governing every other request (#8). The token is fetched once per run and shared across every VU — 50 concurrent VUs produce one grant, under test — and refreshed 30s before expiry. RFC 6749 lets a server take the client credentials as HTTP Basic *or* as form fields and forbids a client sending both, so the first fetch probes Basic and falls back, remembering which convention worked.

  **HMAC signs a documented default with an escape hatch.** `{method}\n{path}\n{timestamp}\n{body_sha256}`, sha256, hex, in `X-Signature` — each part overridable, and `sign:` replaces the canonical string outright over `{method} {path} {query} {body} {body_sha256} {timestamp} {key_id}`. Acceptance green: one fixture flow per scheme under `tests/flows/auth/`, each run end to end against a stub that answers 200 only when the credential arrived intact — the signing stub *recomputes* the signature from what it received, so the test pins the wire rather than the signer's own idea of it — and env-sourced and derived credentials appear in no recorded artifact.
- **Two worked examples against live public APIs.** The existing examples point at a stub we wrote, which proves the engine works against a service designed to make it look good. These point at services nobody here controls.

- **Failure drill-down (issue #38).** A `/runs/{id}/failures` tab that answers "what is actually breaking" before "show me a trace": every failure across the kept traces grouped by **the step it happened in and its cause**, largest group first, each group opening onto the iterations behind it and each of those onto its own waterfall with the span that failed already selected. Two links from a count to the request that produced it.

  The causes are `status`, `assertion`, `extraction`, `timeout`, `connection`, `throttled`, and a residual `error`, recovered the way `Kind` is — spans carry no cause of their own (ADR 0007). **The order they are tried is the design.** A throttle is classified first and can never fall into a generic error group (ADR 0006), even in the modes where a throttle also fails the flow-run and the trace root therefore says `failed`. A status the target refused outranks the assertion that noticed it: "checkout answered 503" is the finding an author acts on, "assert_status failed" is only how it surfaced — and it is blamed on the *step*, so one step's failures don't scatter across every assertion it makes. What is left is the failing span's own nature.

  Two counting rules keep the numbers honest. Only the **deepest** failed span in a trace is reported, because an assertion failure marks both the assertion and the step around it; and one finding per group per trace, because three failed attempts of a retried call are one iteration failing once, not three. (Retry `attempt N` wrappers were also classified as *logic* by `Kind` — they are the call, made again, so they are network now; they had been drawn in the assert/extract colour everywhere.)

- **Spans now carry *why* they failed, not just that they did (extends #19).** The cause taxonomy needed something the store did not hold: a call that got no answer has no status, and only the recorded reason separates a timeout from a refused connection. `Span.SetFailure` holds the engine's own words by reference and `Finalize` materializes them into `Payload.Failure` for kept traces only — the same deferral the bodies and the call identity use, so a dropped trace still costs nothing. **The reason goes through redaction** like a body: a transport error carries the URL it failed on and an assertion mismatch quotes the value it saw. The executor now notes the reason on the span the failure is *about* — the assertion or extraction child, not the step around it — which is also what lets a group link land on the exact row.

  Verified end to end against real runs rather than fixtures: the stress example (a rate-limited stub) drills into `checkout · throttled · HTTP 429` and `checkout · status · HTTP 500` as separate groups, and the login example run with the target down into `login · connection · connection refused`; each iteration link opens its waterfall with the failing span selected, and the env-sourced secret appears in no stored `failure` field.

  That run also killed a share column the page originally had. Capture is deliberately lopsided — every failure is kept whole, throttles are sampled like successes (ADR 0007) — so on the stress run the shares read *throttled 52.6% / status 47.4%* when the truth was 802 throttles against 9 errors. A percentage that confident about a sampled tier is worse than none, so the column is gone and the note states the coverage plainly: counts across causes are a floor, not a comparison.

Every run URL is now project-scoped (`/p/{slug}/runs/{id}`), so two projects can hold runs recorded at the same nanosecond without either shadowing the other; slugs are disambiguated if names collide. The workspace root is a project chooser, but a single-project workspace has nothing to choose so it redirects straight in — `serve --store runs` behaves exactly as before. Within a project, runs are **grouped by scenario**, newest group first, because re-running one scenario is the common case and comparing those runs is the reason to look (the on-ramp to #40's baseline comparison). Breadcrumbs gain a `projects ›` step only when there is more than one.

- **The store now carries the run's own verdict.** Found by running the examples: the CLI printed `error_rate < 1%: ok` and exited 0, while the browser called the same run **failed**. `saveRun` evaluated thresholds and then dropped them, so `meta.json` held only the raw rates and the server had to invent a verdict from `ErrorRate > 0` — which disagrees with the exit code the moment a target has any error floor at all (the stub's is 0.5%). Thresholds and a `breached` flag are now persisted, the verdict reads them, and the overview shows each gate exactly as the CLI printed it. A run with no thresholds declared has nothing to pass or fail and is only described. This is also the prerequisite for #40's threshold flips.

- **Flame graph: full width, and zoom.** The detail panel moved from beside the graph to below it — the graph is the thing being read, so it gets the whole column, with taller rows so labels are legible. Zoom is **re-rooting**, not scaling: `?zoom=<span-path>` makes the focused frame the full width and its children divide that, which is the only thing that makes a sub-percent frame readable. Display depth re-bases to the focused row while kind classification still sees the frame's real depth. A zoom trail walks back out one level at a time, selecting a frame preserves the zoom, and a stale zoom path falls back to the whole graph. Frame URLs are assembled in Go, not markup — html/template refuses to interpolate into a URL built conditionally in a template, which is a good refusal.

- **Captured responses gained their identity (extends #19).** Bodies were already captured and redacted; what was missing was everything about the call itself, so a span could say `failed` without saying *500*. Call spans now carry method, URL, status, `Retry-After`, and request/response sizes, held by reference during the run and materialized only for kept traces — the same deferral the bodies use, so dropped traces still cost nothing. **The URL goes through redaction**: a credential can ride in a query string, and unlike a body the URL is never size-capped away, so scrubbing is the only thing protecting it. `Retry-After` is kept unconditionally because on a throttle it is the server stating how long it wanted to be left alone; the status is toned by class so a 429 reads throttled rather than merely red. Verified end to end: a kept stress trace shows `status 429 · retry_after 1 · outcome throttled`.

- **Fourth storage tier: every flow-run individually (`samples.json`).** The series answers "when", but bucketed; seeing each flow-run needed the records themselves. Capture mirrors the trace policy (ADR 0007) rather than inventing one: every failed, throttled and skipped flow-run is kept whole, successes fill the remaining budget on an even stride so a thinned run still covers its whole duration, and the file states `total`/`kept`/`every_nth` so a sampled view is never read as the whole run. Real runs so far sit well inside it — a 2000-flow-run stress run keeps all 2000 in ~360 KB. The outcomes page draws one square per flow-run, filterable by outcome, and caps rendering at 4000 squares while saying how many it left undrawn.

## 2026-07-21

- **10k-VU generator footprint benchmark (#21).** A re-runnable harness (`internal/executor/bench_test.go`, `-short`-skipped, env-configurable) drives the declarative fast path under the goroutine-per-VU pool and reports throughput, generator CPU, and per-VU memory from the engine's own self-metrics. Reference run on a 10-core laptop: **10,000 concurrent VUs sustained against a 100 ms-latency target with the generator at ~30% CPU (≈70% headroom) and ~69 KiB/VU**, throughput 47.7k iter/s; per-VU footprint holds at 65–69 KiB from 2k to 10k VUs, so it scales linearly. Fills the PRD §18 NFR placeholder (generator CPU < 50%) with a measured baseline; the harness is the regression detector. Written up in docs/benchmarks/10k-vu-footprint.md.

- **Arrival cap is a hard scheduling constraint (ADR 0013, spike #15).** Resolved the PRD open question on how the profile-level `arrival_cap` should be enforced. Prototyped both against the executor and measured (`internal/executor/arrival_spike_test.go`): a **hard** open-loop generator that dispatches on a fixed `1/N` schedule versus a **soft** self-paced closed loop where VUs pace themselves to `N/vus`. At 1000 req/s against a realistic stub (mostly 2 ms, a 100 ms tail every 8th response), the open-loop model held the cap exactly (mean 1000/s, CoV ≈ 0) while the self-paced model undershot by ~11% (889/s) — a slow response stalls a self-pacing VU, and with a fixed VU count nothing compensates, so the achieved rate couples to response time. Decision: enforce as a hard constraint via the open-loop generator (the executor's open arrival model), decoupled from VU count and response time and coordinated-omission correct. #16 implements the planner/executor wiring with a ±5% steady-state tolerance; the open-loop generator cannot exceed the cap by construction. Under-provisioned workers make the rate honestly undershoot as rising latency rather than hide it (Little's law). The measurement harness stays in the tree, skipped under `-short`.

## 2026-07-20

- **Dropped the Go↔Python runtime bridge (ADR 0012, supersedes 0008).** Product call: the bridge — Go calling into a pool of Python worker processes to run `logic` steps, with worker-pool sizing, backpressure, and cross-process pace-guard coordination — was the project's hardest, riskiest subsystem, and the declarative fast path already covers integration/load/stress/soak without it. Removed it and the general `logic` step. Execution is now two independent producers sharing one contract — the span model and run store: the **Go engine** (`flowbench run`) runs YAML and declarative Python at full VU scale with no runtime Python, and the **Python SDK** (`python file.py`) drives its own flow and writes runs. Prompt observation survives, re-homed to the Python-driven path (ADR 0009 rewritten): the team's LLM call is wrapped where it already runs — in Python — so pace guards coordinate in-process and no bridge is reached; the honest cost is that prompt-observing runs are integration/diff-scale, not 10k-VU, which was already their nature (Python-surface-only, paced). The trade we took on: the run-store format becomes a versioned public contract two producers must agree on — a data-format discipline problem instead of a concurrency/IPC one. Cascaded through the PRD (§9 model + ERD, §10.1/§10.5/§10.9, §11 boundary, §13 executor + architecture diagram, §14, §16, §17 deps/risks/open-questions, §19 milestone table) and the milestone plan; M1 loses the bridge spike (#10). Issues #10/#23/#24 close; the prompt-observation issues (#43/#44/#45) stay, re-scoped to Python-driven; the IR loses `StepLogic`/`LogicSpec` in a follow-up.
- **`flowbench run` — the M1 tracer bullet (issue #9).** The local dev loop, wiring the whole engine together: `flowbench run <scenario.yaml> --target <name>` parses and validates the flow, resolves the target (a name → `<targets-dir>/<name>.yaml`, an explicit path, or the zero-config `local` default of `http://localhost:8080`), runs the pre-run host allow-list gate, loads data pools relative to the scenario file, then executes at one VU — once, or once per fixture row — printing a per-iteration line and a terse summary. The Runner gained an `Allow` hook wired to the target's `Allows`, so a call whose host resolves outside the allow-list is refused before it is sent, not just caught pre-run — closing the dynamic-host gap #8 left for runtime. Exit codes are a contract: `0` pass, `1` recorded failures, `2` pre-run error (bad args, parse/validate, or the safety gate). Acceptance green: the chained checkout runs both fixture rows against a local stub with ~30ms startup-to-summary (well under a second); a failing assertion exits `1` naming the step; a missing scenario and an external-host call each exit `2`.
- **Target configs + host allow-list gate (issue #8, ADR 0005/0010).** A run names a target with `--target <name>`, resolving to `<dir>/<name>.yaml` — base URLs (the host allow-list), VU/RPS ceilings, an optional agent address, and disallowed modes; never credentials. Parsing stays in `internal/parser` per ADR 0010 (goccy confined there): `ParseTargetFile` converts YAML to canonical JSON and strict-decodes into `ir.TargetConfig` via the new `ir.DecodeTargetConfig`, so an unknown key fails loudly, then validates. The new dependency-free `internal/target` package turns a config into the safety gate: `BaseURL()` is the default relative calls resolve against (the first base URL); `Check(scenario)` is the pre-run gate that refuses, before any request is sent, a flow whose statically-knowable call host falls outside the allow-list or whose mode the target disallows — naming the offending step and host; `Allows(url)` is the request-time primitive for URLs whose host is only known after templating (wired into the Runner in #9). Ceilings ride along for the planner (M2). Acceptance green: a flow calling `http://evil.example/...` under `--target local` is refused pre-run; relative, allowed-absolute, and dynamic-host calls pass; a target's disallowed mode is refused.
- **Data pools (issue #7).** New `internal/data` package: fixture loaders plus a concurrency-safe dispenser. `Load` reads a CSV or JSON source (format inferred from the extension, overridable), CSV mapping the header row to fields — the checked-in `users.csv` carries a JSON array in a quoted `cart` field, which round-trips — and JSON taking an array of objects, coercing non-scalar values to their JSON text so templates inject them verbatim. A `Pool` dispenses rows through a mutex under three distributions: unique-per-vu (a distinct row per draw, the default), round-robin (wraps forever), and random (seeded, so draws are reproducible). Exhaustion applies to unique-per-vu — `fail` (default) returns `ErrExhausted`, `cycle` wraps to the top, `stop` signals done. Uniqueness under concurrency is the engine's responsibility, not the flow author's. Acceptance green (with `-race`): 300 concurrent consumers of a unique-per-vu pool each get a distinct row and none repeats; each exhaustion policy behaves as configured. The Runner/CLI will draw one row per VU into a fresh `Scope` in #9.
- **CI gate.** GitHub Actions runs gofmt / vet / build / `test -race` on every PR and push to main, on the go.mod Go version; a branch ruleset makes `build & test` a required check and protects main from force-push and deletion.
- **`{{ env.* }}` resolution and redaction (issue #6, ADR 0005).** Credentials come from the environment, never a bespoke secrets file — so any value the flow sources from `{{ env.* }}` is a secret that must not reach storage. Resolution already landed with the Scope in #5; this closes the loop with the redaction side. New `internal/secret` package: a thread-safe `Set` (VUs share one per run) that registers secret values and scrubs them from arbitrary text, replacing each with `[redacted]` and matching longest-first so overlapping secrets can't leave a placeholder mid-value. `Scope.Resolve` registers every env-resolved value into the scope's `Set` as it hands the value to the templater, and `Scope.Secrets()` exposes it. The executor now redacts at the artifact boundary: `record` runs every failure detail — transport errors (which can carry a secret-bearing URL), extraction misses, and assertion mismatches (whose actual value may be an echoed credential) — through the redactor before it becomes a stored `Failure`. Spans stay secret-free by construction in M1 (names are structural, no payloads yet); the M2 capture path (#19) will run captured request/response bodies through the same `scope.Secrets()`. Env values are redacted verbatim regardless of length, so sourcing non-secret config from env means it is scrubbed from artifacts too — the secure default. Acceptance green (with `-race`): a flow injects an env credential into a live request that a leaky stub echoes back; the credential is registered as a secret, the request still authenticates, and the raw value appears in no recorded artifact — the forced-failure detail shows `[redacted]`.
- **Extract / assert / template chaining (issue #5, ADR 0011).** The chaining primitive that makes a flow more than a list of calls: extract values from one response into flow variables, inject them into later requests, assert on the result. Two new packages. `internal/eval` is adapter-neutral and dependency-free: a hand-rolled JSONPath subset (`$.a.b`, `$['a.b']`, `$.a[0]`, negative indices; filters/wildcards/recursive-descent rejected at parse time — ADR 0011), assertion evaluation across all five sources (status, latency, header, body, var) and ten ops (eq/ne/lt/lte/gt/gte/contains/matches/exists/not_exists) with numeric coercion and duration-aware latency compares, and extraction over a small `Target` interface so M3's GraphQL/gRPC adapters reuse it. `internal/executor` gains `Scope` (env / bound data-pool row / extracted vars, with the templating resolver injection uses) and a single-iteration `Runner` that chains a flow's call and wait steps: build request → adapter `Do` → extract (populating scope) → assert, emitting one child span per extraction and assertion under the step span. Failure handling honors `on_failure` with the PRD section 12 mode-aware default (loud/abort_flow in integration/system, recorded data in load/stress/soak); a failure is always recorded in the iteration regardless, and `abort_run` flags the whole run to stop. The M2 goroutine-per-VU pool will drive many of these concurrently. Acceptance green: the PRD section 11 chained checkout (login → extract token → authenticated order → extract id → pay → assert 202) runs end to end against a stub; a failing assertion is recorded per iteration; the integration default stops the flow at the first failure.
