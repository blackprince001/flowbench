- **Two worked examples against live public APIs.** The existing examples point at a stub we wrote, which proves the engine works against a service designed to make it look good. These point at services nobody here controls.

  **`examples/deck-of-cards`** is the chaining showcase, against [deckofcardsapi.com](https://deckofcardsapi.com) — free, no key, and genuinely *stateful*: a shuffled deck lives on the server under an id and the cards you draw are gone from it. Shuffle → keep the id → draw from *that* deck → build a pile → read it back is the login/token/act pattern without the auth, and the state is what a fixed JSON endpoint cannot demonstrate: after drawing two cards the deck really does assert `remaining == 52 - 2`. It covers extraction, injection into both a path and a composed query value, all five assertion sources, `matches`/`contains`/`!= null`, a `wait` step, a data pool dealing a different hand per row, and the target rails (allow-list, ceilings, `disallowed_modes` refusing stress pre-run).

  **`examples/httpbingo`** is the failure showcase, against [httpbingo.org](https://httpbingo.org) — a service that exists to be tested against, so every failure is one you asked for. `faults.flow.yaml` produces **all eight drill-down groups in a single run**: 500 and 402 as separate `status` groups, 429 and a step-mapped 503 as separate `throttled` groups, a wrong body as `assertion`, a missing field as `extraction`, `/delay/5` as `timeout`, and `https://nothing.invalid` (RFC 2606, never resolves, no server troubled) as `connection`. `resilience.flow.yaml` calls a weighted-failure endpoint twice per iteration, once retried and once not, so the run is its own control — the retried step contributes no failure group at all while the unguarded one gets a `status · HTTP 503` group, which is the argument for the policy stated as data rather than prose.

  Both are deliberately small — a few VUs for a few seconds, a couple of hundred requests — and both READMEs say plainly that real scale belongs against the local stub, because a free service should not have to absorb a stress run. Every claim in them was executed before it was written: the exit-2 refusal, the eight groups, the retry contrast, and the redaction check. That last one caught a lie in its own first draft — `grep runs/` after an *integration* run proves nothing, since integration mode prints and exits without writing an artifact at all, so the echo scenario now runs a small load profile precisely so there are stored traces in which the env-sourced credential really is `[redacted]`.

- **A call now has a budget (`request_timeout` on the target).** Found while building the above: the HTTP client timeout was the adapter's 30s default with nothing able to change it, so a host that accepts a connection and then says nothing holds a VU for half a minute — and the drill-down's `timeout` cause was unreachable in practice, because nothing could produce one inside a normal run. It belongs to the *target* rather than the scenario: a service that cannot answer inside two seconds is failing, whatever the flow asks of it. Threaded through `ir.TargetConfig` → `executor.Options` → both `adapters.NewSession` call sites and the single-VU path, with a test asserting several flow-runs fit inside a run pointed at a server that never answers.

- **The results server is three columns now.** Runs and projects on the left, the flow in the middle, whatever is selected on the right. Every page used to carry its own two-column `.split` with a detail panel bolted to one section, so "the thing I clicked" appeared in a different place on every view. It has one place now: pages fill the rail through a `detail` template the layout renders, and a page with nothing to inspect (the project list, the run list) emits nothing at all, so `:empty` collapses the column rather than leaving a 340px gap. Compare has nothing individual to show either, but it says so rather than vanishing — two whole runs side by side is not a thing inside a run. Both outer columns collapse from the topbar, persisted in `localStorage` and applied in `<head>` so a collapsed rail never flashes open first; the middle column has a reading width of its own instead of stretching a table across a whole wide screen. **Narrow screens keep exactly what they had**: one stacked column, and both rails forced back on — a state collapsed on a desktop must not hide the navigation where there is no column to collapse into. The left column also switches projects now, which previously meant a trip back to the workspace root; a single-project workspace is not offered the choice.

- **Overview and dashboard are one page.** They were two tabs of one question — the rates in one, the shape that produced them in the other — so a run now reads top to bottom: summary tiles, the outcome strip, the charts, drift for a soak, the per-step table, the gates, then the ways in. `/dashboard` is a permanent redirect carrying its query, so existing links keep working.

- **Charts you can actually read.** They were 118px in a four-up grid, and the only way to enlarge one was to click its *title*. The grid is wider, the plots are half again as tall, and the whole card is the target with the expand affordance surfacing on hover. Opening one (`?chart=latency`) gives it the card at full height with a labelled y axis, quarter-hour ticks across the run, a rule at its highest point named in words above the plot, and per-series min/mean/max/last — the detail a small multiple has no room for. Server-rendered and URL-addressable like the flame graph's zoom (ADR 0014), so it is shareable and needs no script.

- **The interface has a face: Open Runde.** A soft, rounded cut of Inter (SIL OFL 1.1), subset to latin/latin-ext at three weights and shipped in the binary — about 200 KB — served as files under `/assets/` with an immutable cache header rather than inlined, since the stylesheet is inlined into *every* page and an inlined font would ride along with it each time. The system stack stays behind it, so a glyph outside the subset falls back per glyph instead of failing. The mono stays the platform's own: machine facts should look like a terminal, and it costs nothing to ship. A rounded monospace (Sono) was tried alongside it and dropped — the pairing was not worth a second font in the binary.

- **Failure drill-down (issue #38).** A `/runs/{id}/failures` tab that answers "what is actually breaking" before "show me a trace": every failure across the kept traces grouped by **the step it happened in and its cause**, largest group first, each group opening onto the iterations behind it and each of those onto its own waterfall with the span that failed already selected. Two links from a count to the request that produced it.

  The causes are `status`, `assertion`, `extraction`, `timeout`, `connection`, `throttled`, and a residual `error`, recovered the way `Kind` is — spans carry no cause of their own (ADR 0007). **The order they are tried is the design.** A throttle is classified first and can never fall into a generic error group (ADR 0006), even in the modes where a throttle also fails the flow-run and the trace root therefore says `failed`. A status the target refused outranks the assertion that noticed it: "checkout answered 503" is the finding an author acts on, "assert_status failed" is only how it surfaced — and it is blamed on the *step*, so one step's failures don't scatter across every assertion it makes. What is left is the failing span's own nature.

  Two counting rules keep the numbers honest. Only the **deepest** failed span in a trace is reported, because an assertion failure marks both the assertion and the step around it; and one finding per group per trace, because three failed attempts of a retried call are one iteration failing once, not three. (Retry `attempt N` wrappers were also classified as *logic* by `Kind` — they are the call, made again, so they are network now; they had been drawn in the assert/extract colour everywhere.)

- **Spans now carry *why* they failed, not just that they did (extends #19).** The cause taxonomy needed something the store did not hold: a call that got no answer has no status, and only the recorded reason separates a timeout from a refused connection. `Span.SetFailure` holds the engine's own words by reference and `Finalize` materializes them into `Payload.Failure` for kept traces only — the same deferral the bodies and the call identity use, so a dropped trace still costs nothing. **The reason goes through redaction** like a body: a transport error carries the URL it failed on and an assertion mismatch quotes the value it saw. The executor now notes the reason on the span the failure is *about* — the assertion or extraction child, not the step around it — which is also what lets a group link land on the exact row.

  Verified end to end against real runs rather than fixtures: the stress example (a rate-limited stub) drills into `checkout · throttled · HTTP 429` and `checkout · status · HTTP 500` as separate groups, and the login example run with the target down into `login · connection · connection refused`; each iteration link opens its waterfall with the failing span selected, and the env-sourced secret appears in no stored `failure` field.

  That run also killed a share column the page originally had. Capture is deliberately lopsided — every failure is kept whole, throttles are sampled like successes (ADR 0007) — so on the stress run the shares read *throttled 52.6% / status 47.4%* when the truth was 802 throttles against 9 errors. A percentage that confident about a sampled tier is worse than none, so the column is gone and the note states the coverage plainly: counts across causes are a floor, not a comparison.

- **10k-VU generator footprint benchmark (#21).** A re-runnable harness (`internal/executor/bench_test.go`, `-short`-skipped, env-configurable) drives the declarative fast path under the goroutine-per-VU pool and reports throughput, generator CPU, and per-VU memory from the engine's own self-metrics. - **Arrival cap is a hard scheduling constraint (ADR 0013, spike #15).** Resolved the PRD open question on how the profile-level `arrival_cap` should be enforced. Prototyped both against the executor and measured (`internal/executor/arrival_spike_test.go`): a **hard** open-loop generator that dispatches on a fixed `1/N` schedule versus a **soft** self-paced closed loop where VUs pace themselves to `N/vus`. At 1000 req/s against a realistic stub (mostly 2 ms, a 100 ms tail every 8th response), the open-loop model held the cap exactly (mean 1000/s, CoV ≈ 0) while the self-paced model undershot by ~11% (889/s) — a slow response stalls a self-pacing VU, and with a fixed VU count nothing compensates, so the achieved rate couples to response time. Decision: enforce as a hard constraint via the open-loop generator (the executor's open arrival model), decoupled from VU count and response time and coordinated-omission correct. #16 implements the planner/executor wiring with a ±5% steady-state tolerance; the open-loop generator cannot exceed the cap by construction. Under-provisioned workers make the rate honestly undershoot as rising latency rather than hide it (Little's law). The measurement harness stays in the tree, skipped under `-short`.

- **Dropped the Go↔Python runtime bridge (ADR 0012, supersedes 0008).** Product call: the bridge — Go calling into a pool of Python worker processes to run `logic` steps, with worker-pool sizing, backpressure, and cross-process pace-guard coordination — was the project's hardest, riskiest subsystem, and the declarative fast path already covers integration/load/stress/soak without it. Removed it and the general `logic` step. Execution is now two independent producers sharing one contract — the span model and run store: the **Go engine** (`flowbench run`) runs YAML and declarative Python at full VU scale with no runtime Python, and the **Python SDK** (`python file.py`) drives its own flow and writes runs. The trade we took on: the run-store format becomes a versioned public contract two producers must agree on — a data-format discipline problem instead of a concurrency/IPC one. - **`flowbench run` — the M1 tracer bullet (issue #9).** The local dev loop, wiring the whole engine together: `flowbench run <scenario.yaml> --target <name>` parses and validates the flow, resolves the target (a name → `<targets-dir>/<name>.yaml`, an explicit path, or the zero-config `local` default of `http://localhost:8080`), runs the pre-run host allow-list gate, loads data pools relative to the scenario file, then executes at one VU — once, or once per fixture row — printing a per-iteration line and a terse summary. The Runner gained an `Allow` hook wired to the target's `Allows`, so a call whose host resolves outside the allow-list is refused before it is sent, not just caught pre-run — closing the dynamic-host gap #8 left for runtime. Exit codes are a contract: `0` pass, `1` recorded failures, `2` pre-run error (bad args, parse/validate, or the safety gate). Acceptance green: the chained checkout runs both fixture rows against a local stub with ~30ms startup-to-summary (well under a second); a failing assertion exits `1` naming the step; a missing scenario and an external-host call each exit `2`.
- **Target configs + host allow-list gate (issue #8, ADR 0005/0010).** A run names a target with `--target <name>`, resolving to `<dir>/<name>.yaml` — base URLs (the host allow-list), VU/RPS ceilings, an optional agent address, and disallowed modes; never credentials. Parsing stays in `internal/parser` per ADR 0010 (goccy confined there): `ParseTargetFile` converts YAML to canonical JSON and strict-decodes into `ir.TargetConfig` via the new `ir.DecodeTargetConfig`, so an unknown key fails loudly, then validates. The new dependency-free `internal/target` package turns a config into the safety gate: `BaseURL()` is the default relative calls resolve against (the first base URL); `Check(scenario)` is the pre-run gate that refuses, before any request is sent, a flow whose statically-knowable call host falls outside the allow-list or whose mode the target disallows — naming the offending step and host; `Allows(url)` is the request-time primitive for URLs whose host is only known after templating (wired into the Runner in #9). Ceilings ride along for the planner (M2). Acceptance green: a flow calling `http://evil.example/...` under `--target local` is refused pre-run; relative, allowed-absolute, and dynamic-host calls pass; a target's disallowed mode is refused.
- **Data pools (issue #7).** New `internal/data` package: fixture loaders plus a concurrency-safe dispenser. `Load` reads a CSV or JSON source (format inferred from the extension, overridable), CSV mapping the header row to fields — the checked-in `users.csv` carries a JSON array in a quoted `cart` field, which round-trips — and JSON taking an array of objects, coercing non-scalar values to their JSON text so templates inject them verbatim. A `Pool` dispenses rows through a mutex under three distributions: unique-per-vu (a distinct row per draw, the default), round-robin (wraps forever), and random (seeded, so draws are reproducible). Exhaustion applies to unique-per-vu — `fail` (default) returns `ErrExhausted`, `cycle` wraps to the top, `stop` signals done. Uniqueness under concurrency is the engine's responsibility, not the flow author's. Acceptance green (with `-race`): 300 concurrent consumers of a unique-per-vu pool each get a distinct row and none repeats; each exhaustion policy behaves as configured. The Runner/CLI will draw one row per VU into a fresh `Scope` in #9.
- **CI gate.** GitHub Actions runs gofmt / vet / build / `test -race` on every PR and push to main, on the go.mod Go version; a branch ruleset makes `build & test` a required check and protects main from force-push and deletion.
- **`{{ env.* }}` resolution and redaction (issue #6, ADR 0005).** Credentials come from the environment, never a bespoke secrets file — so any value the flow sources from `{{ env.* }}` is a secret that must not reach storage. Resolution already landed with the Scope in #5; this closes the loop with the redaction side. New `internal/secret` package: a thread-safe `Set` (VUs share one per run) that registers secret values and scrubs them from arbitrary text, replacing each with `[redacted]` and matching longest-first so overlapping secrets can't leave a placeholder mid-value. `Scope.Resolve` registers every env-resolved value into the scope's `Set` as it hands the value to the templater, and `Scope.Secrets()` exposes it. The executor now redacts at the artifact boundary: `record` runs every failure detail — transport errors (which can carry a secret-bearing URL), extraction misses, and assertion mismatches (whose actual value may be an echoed credential) — through the redactor before it becomes a stored `Failure`. Spans stay secret-free by construction in M1 (names are structural, no payloads yet); the M2 capture path (#19) will run captured request/response bodies through the same `scope.Secrets()`. Env values are redacted verbatim regardless of length, so sourcing non-secret config from env means it is scrubbed from artifacts too — the secure default. Acceptance green (with `-race`): a flow injects an env credential into a live request that a leaky stub echoes back; the credential is registered as a secret, the request still authenticates, and the raw value appears in no recorded artifact — the forced-failure detail shows `[redacted]`.
- **Extract / assert / template chaining (issue #5, ADR 0011).** The chaining primitive that makes a flow more than a list of calls: extract values from one response into flow variables, inject them into later requests, assert on the result. Two new packages. `internal/eval` is adapter-neutral and dependency-free: a hand-rolled JSONPath subset (`$.a.b`, `$['a.b']`, `$.a[0]`, negative indices; filters/wildcards/recursive-descent rejected at parse time — ADR 0011), assertion evaluation across all five sources (status, latency, header, body, var) and ten ops (eq/ne/lt/lte/gt/gte/contains/matches/exists/not_exists) with numeric coercion and duration-aware latency compares, and extraction over a small `Target` interface so M3's GraphQL/gRPC adapters reuse it. `internal/executor` gains `Scope` (env / bound data-pool row / extracted vars, with the templating resolver injection uses) and a single-iteration `Runner` that chains a flow's call and wait steps: build request → adapter `Do` → extract (populating scope) → assert, emitting one child span per extraction and assertion under the step span. Failure handling honors `on_failure` with the PRD section 12 mode-aware default (loud/abort_flow in integration/system, recorded data in load/stress/soak); a failure is always recorded in the iteration regardless, and `abort_run` flags the whole run to stop. The M2 goroutine-per-VU pool will drive many of these concurrently. Acceptance green: the PRD section 11 chained checkout (login → extract token → authenticated order → extract id → pay → assert 202) runs end to end against a stub; a failing assertion is recorded per iteration; the integration default stops the flow at the first failure.
